# "快乐能源"联机游戏 — 开发设计文档

- 版本：v1.0（2026-09-02）
- 依据规则：《附件-"快乐能源"游戏规则 v2.7.2》（2026-09-01，配套辅助计算表 v2.12）
- 状态：待用户评审

---

## 1. 项目概述

### 1.1 背景

"快乐能源"是一款能源系统规划教育桌游：玩家分饰绿色城市"自强城"中的 7 种角色组成小组，用 2 轮"规划→结算"完成源网荷储协同部署，多支小组同场竞争终极总分。目前流程依赖纸质表格人工计算，结算慢、易算错、骰子与事件卡管理繁琐。

本项目将规则完整数字化为一个**局域网多人联机游戏**：玩家用手机浏览器操作，主持人大屏展示全局，服务端权威完成校验、随机与结算。

### 1.2 目标

1. **规则 100% 数字化**：规则文档中的每个行动、资源限制、随机机制、事件卡、目标卡、计分公式都在软件中生效，且与文档逐一对应。
2. **多人联机**：一个房间 2–8 支队伍同场竞技，Socket.IO 实时同步。
3. **公正随机**：骰子、事件卡、目标卡全部由服务端随机产生，客户端不可预测、不可篡改。
4. **限制强制**：资金、土地、输配上限、行动不得重复、特批权次数等限制由软件强制执行。
5. **透明结算**：结算明细逐步展示，玩家能看懂每一分的来源。
6. **跨队评比**：实时排行榜与终局颁奖。

### 1.3 非目标（本期不做）

- 公网部署、账号系统、注册登录
- 多语言界面（仅中文）
- 对局回放、历史房间云端存储
- AI 机器人填充队伍
- 移动 App 打包（浏览器 PWA 也不做）

### 1.4 成功标准

- 用 3 个浏览器窗口（2 名玩家 + 1 主持人）完整走完 2 轮对局，结算结果与手工按规则文档计算一致。
- 引擎单元测试覆盖全部结算路径与校验规则。
- 断网重连、进程重启恢复后游戏状态不丢。

## 3. 游戏规则规格（引擎的权威依据）

> 本章是 `data/*.json` 配置与结算引擎的唯一依据，数值与规则文档 v2.7.2 逐条对应。

### 3.1 角色

| 代码 | 角色 | 定位 | 计分 |
|------|------|------|------|
| GENERATION | 新能源发电企业 | 源 | 是 |
| GRID | 电网企业 | 网/储 | 是 |

每队必须 7 名标准角色全部就位才可开始（主持人可"强制开始"，缺位角色当轮视为放弃）；精算师席位 0 或 1 人。

### 3.2 初始资源（全队共享）

| 资源 | 数值 | 说明 |
|------|------|------|
| 资金 | 100 单位/轮 | 每轮独立发放，未用完清零（事件卡可改变，见 3.6） |
| 土地 | 12 单位 | 两轮共用同一指标 |
| 输配上限 | 初始 3 点 | 行动耗电量 > 当前有效输配上限 → 该行动**不可执行** |
| 储能上限 | 初始 2 点 | 累计储能容量，跨轮累计 |

有效输配上限 = 3 + 扩建智能电网次数×4 +（当轮有柔性电网调度 ? 2 : 0）。

### 3.3 行动总表（20 项）

**发电企业（源）** — 个人分 = 两轮绿电产出合计：

| 行动 | 产出 | 分数 | 成本 |
|------|------|------|------|
| 集中式光伏 | 稳定 8 点绿电 | +8 | 资金 25 土地 2 |
| 深远海风电 | 掷骰 ≥4 产出 15 点；<4 保底 5 点 | 成功 +15 / 保底 +5 | 资金 35 土地 3 |
| 先进核电站 | 稳定 10 点（免疫极端气候） | +10 | 资金 35 土地 3 |

**电网企业（网/储）** — 个人分 = 扩建次数×4 + 储能电站次数×4 + 柔性调度次数×3：

| 行动 | 产出 | 分数 | 成本 |
|------|------|------|------|
| 扩建智能电网 | 输配上限 +4（永久） | +4 | 资金 20 土地 1 |
| 建设储能电站 | 储能容量 +4（免疫寒潮，吸收弃电） | +4 | 资金 25 土地 2 |
| 柔性电网调度 | 当轮输配上限 +2（仅当轮）；合法弃电额度 +2 | +3 | 资金 15 |

**新能源汽车企业（荷）** — 个人分 = 两轮实际消耗合计×1 + V2G 加分：

| 行动 | 消耗 | 分数 | 成本 |
|------|------|------|------|
| 批量生产电动车 | 5 点 | 实际消耗×1（若此前建过超级快充，再 +2） | 资金 25 |
| 扩建快充网络 | 3 点 | 实际消耗×1 | 资金 15 土地 1 |
| 车网互动 V2G 研发 | 2 点 | 实际消耗×1；掷骰 ≥3 储能 +2（成功 +4 分），<3 储能 +1（失败 +1 分），均计入总储能容量 | 资金 15 |
| 新建超级快充网络 | 7 点 | 实际消耗×1；其后"批量生产电动车"+2 分 | 资金 40 土地 3 |

**智能建筑企业（荷）** — 个人分 = 两轮实际消耗合计×1：

| 行动 | 消耗 | 分数 | 成本 |
|------|------|------|------|
| 新建零碳楼宇 | 6 点 | 实际消耗×1 | 资金 20 土地 2 |
| 既有建筑节能改造 | 2 点 | 实际消耗×1；返还全队 5 资金 | 资金 20 |
| 全域立体绿化 | 4 点 | 实际消耗×1；终局全队 +5 分 | 资金 25 |
| 地标级零碳综合体 | 7 点 | 实际消耗×1；其后"全域立体绿化"成本 −10 | 资金 45 土地 3 |

**智能材料企业（智/赋能）** — 个人分 = 科技节省总资金 ÷5（向下取整）：

| 行动 | 产出 | 成本 |
|------|------|------|
| 钙钛矿光伏材料 | 本轮及后续"发电类行动"建造成本 −10 | 资金 10 |
| 轻质绿色建材 | 本轮及后续"建筑类行动"建造成本 −10 | 资金 10 |
| 全链降本工艺 | 本轮全队所有行动成本各减 5（成本不足 5 按实际减免；放弃与零成本行动无减免、不计节省） | 资金 10 |

材料个人分**仅统计材料科技带来的降本**；突发事件减免与城长特批不计入。

**发改委（政/调控）** — 个人分 = 其余 5 名计分队友个人分之和÷4（向下取整）+ 第 2 轮结余资金÷10（向下取整）：

| 行动 | 产出 | 分数影响 | 成本 |
|------|------|------|------|
| 绿电补贴政策 | 纯政策 | 发电、电网**个人分**各 +4 | 资金 20 |
| 容量电价机制 | 全队 +25 资金 | 汽车、建筑**个人分**各 −2 | 无 |
| 绿色招商引资 | 全队 +30 资金（计入当轮可用） | 无 | 土地 2 |

**城长**：每轮 1 次市长特批权——指定 1 项行动减免 5 资金，或总预算超支 ≤5 点特批通过。两项二选一，每轮限一次，软件强制。

### 3.4 成本计算管线

```
有效成本 = max(0, 基础成本
             − 材料定向折扣（钙钛矿/轻质，命中且在生效轮内，各 −10）
             − 全链降本（当轮若有，−5）
             − 事件减免（绿色消费潮：汽车/建筑各 −10；产学研大突破：材料研发归 0）
             − 特效折扣（此前建过地标级零碳综合体：全域立体绿化 −10）
             − 城长特批（若用于本行动，−5））
```

各折扣来源分别记账：材料定向折扣与全链降本的节省额累计进"材料科技节省"（供材料计分）；事件减免与特批单独记账（不计入材料分）。

### 3.5 校验规则（服务端强制）

选行动时实时提示、全员锁定或倒计时归零后终审：

1. 每角色每轮 1 项行动（唯一例外：产学研大突破事件下，材料企业当轮可锁定 2 项研发）；第 2 轮行动池排除第 1 轮已选项（不得重复）。
2. **输配上限硬拦截**：行动耗电量 > 当前有效输配上限 → 不可选。
3. 资金池：Σ当轮全部有效成本 ≤ 当轮可用资金；不足时需城长特批"超支放行"（超支 ≤5 点），或特批"单项减免 5 资金"。
4. 土地：两轮累计占用 ≤ 12。
5. 声明放弃：合法，无产出无消耗。
6. 终审不通过 → 阻止进入结算；主持人可将违规行动强制改为"放弃"。
7. 特批权每轮 1 次、骰子不可重掷、产学研事件外不可双研发——均由软件结构天然阻止。

### 3.6 突发事件卡（每轮 1 张，全场相同，服务端在规划阶段开始时自动抽取）

第 1 轮池（启动机遇）：

| 卡 | 效果 |
|----|------|
| 专项绿色国债 | 第 1 轮全队初始资金**提升至** 125（非 +25） |
| 产学研大突破 | 材料本轮研发免费（0 资金），且可同时执行 2 项研发（唯一合法双研发） |
| 绿色消费潮 | 本轮汽车、建筑项目成本各减免 10 |

第 2 轮池（系统考验）：

| 卡 | 效果 |
|----|------|
| 极寒无风寒潮 | 第 2 轮发电产出优先从光伏 −3；无光伏则从风电（掷骰后产出）−3；核电免疫；发电个人分同步 −3；全队建有储能电站（任一轮建成）额外 +5 分 |
| 现货电价暴涨 | 第 1 轮储能电量每点 +2 分；第 2 轮弃电罚分每点 ×4 |
| 零碳城市先锋认证 | 若两轮（发电产出 − 实际消耗）均 ≤2，且本局实施过绿色招商引资，全队额外 +8 分 |

### 3.7 城市目标卡（6 张；开局每队随机发 2 张、城长自选保留 1 张；终局达成 +5）

| 卡 | 达成条件 |
|----|----------|
| 储能达人 | 累计总储能容量 ≥6 且 两轮入储合计 ≥2 |
| 负荷先锋 | 两轮实际消耗合计 ≥15 |
| 追风者 | 选过深远海风电 且 两轮实际消耗合计 ≥10 |
| 无风之城 | 全程未选深远海风电 且 两轮总绿电 ≥10 且 弃电量为 0 |
| 花园城市 | 执行过地标级零碳综合体 且 每轮弃电量均 ≤2 |
| 资金管家 | 第 2 轮结余资金 ≥70 |

目标卡不计入各角色个人分，只加在团队总分。两张候选卡和城长保留的最终目标卡全场公开。

### 3.8 掷骰

结算阶段开始的瞬间，服务端为每队一次性掷出本队需要的骰子（深远海风电、V2G），`crypto.randomInt(1, 7)`；全场播放骰子动画后才亮结果。骰子影响产出与分数，随后进入结算计算。

### 3.9 轮结算算法

```
输入：当轮行动、骰子结果、事件卡、累计状态（储能容量、第1轮储能电量等）

发电产出 = Σ发电行动产出（骰后）         # 寒潮在此扣减
可用绿电 = 发电产出 + (第2轮 ? 第1轮储能电量 : 0)
计划消耗 = Σ荷侧行动计划消耗
实际消耗 = min(计划消耗, 可用绿电)        # 电力不足按申报顺序分配，缺口显著标注
储能入量 = min(可用绿电 − 实际消耗, 累计储能容量)   # 先入蓄水池；容量含当轮新增（储能电站/V2G）
弃电量   = 可用绿电 − 实际消耗 − 储能入量           # 蓄满才计弃电（含合法弃电）
计罚弃电 = max(0, 弃电量 − 合法弃电额度)            # 柔性调度额度，计入弃电量但免罚
弃电罚分 = 计罚弃电 × (现货暴涨 ? 4 : 2)
```

### 3.10 个人分（两轮累计）

| 角色 | 公式 |
|------|------|
| 发电 | 两轮产出合计 +（绿电补贴 ? 4 : 0）+（寒潮 ? −3 : 0） |
| 电网 | 扩建×4 + 储能电站×4 + 柔性调度×3 +（绿电补贴 ? 4 : 0） |
| 汽车 | 两轮实际消耗合计 + V2G(+4/+1) +（超级快充后批量生产 ? +2 : 0）+（容量电价 ? −2 : 0） |
| 建筑 | 两轮实际消耗合计 +（容量电价 ? −2 : 0） |
| 材料 | floor(科技节省总资金 ÷ 5) |
| 发改委 | floor(其余 5 名计分队友个人分和 ÷ 4) + floor(第 2 轮结余资金 ÷ 10) |
| 精算师 | = 发改委（不计入团队总分） |

### 3.11 团队终极总分与排名

```
小组终极总分 = Σ6名计分角色个人分
             + 总储能电量（两轮入储合计）×1
             − 总弃电罚分
             + 额外加分（全域立体绿化 +5；两轮弃电罚分均为0 +5；目标卡达成 +5；
                        先锋认证 +8；现货暴涨时第1轮储能电量×2；寒潮且有储能电站 +5）
```

排名按终极总分降序；并列时先比"消纳模块净值"（= 终极总分 − 个人分总和），仍并列则显示并列名次，由主持人按规则加赛。

## 4. 系统架构

### 4.1 总体

单进程 Node.js，服务端为唯一权威：全部校验、随机、结算在服务端；客户端是"显示器 + 操作面板"。状态存内存，每次变更写 JSON 快照。

### 4.2 目录结构

```
smart-energy/
├── server.js                  # 入口：Express 静态文件 + Socket.IO 挂载
├── package.json
├── src/
│   ├── rooms.js               # 房间生命周期、4位房间码、玩家 token 与断线重连
│   ├── persistence.js         # JSON 快照（每次变更落盘 data/snapshots/）+ 终局导出 JSON/CSV
│   ├── net/protocol.js        # 全部 Socket.IO 事件名与载荷定义（单一出处）
│   └── game/
│       ├── constants.js       # 角色、阶段、初始资源
│       ├── state.js           # 状态机：阶段流转、服务端倒计时
│       ├── actions.js         # 加载 data/actions.json，成本管线、可行性校验
│       ├── engine.js          # 行动选择/锁定/放弃/特批 的校验与执行
│       ├── settlement.js      # 3.9 结算算法 + 3.10/3.11 计分
│       ├── events.js          # 事件卡效果注入
│       ├── goals.js           # 目标卡发牌与达成判定
│       └── random.js          # crypto 骰子、Fisher–Yates 洗牌
├── data/
│   ├── config.json            # 规划时长（默认15分钟）、警示时点、端口等
│   ├── actions.json           # 3.3 行动总表
│   ├── events.json            # 3.6 事件卡
│   └── goals.json             # 3.7 目标卡
├── public/
│   ├── index.html             # 加入页
│   ├── play/                  # 玩家手机端
│   └── host/                  # 主持人大屏端
└── tests/                     # Node 内置 test runner
```

### 4.3 组件职责

| 组件 | 职责 | 依赖 |
|------|------|------|
| rooms | 建房/加入/角色分派/重连 token | random |
| state | LOBBY→…→FINISHED 流转、倒计时 | rooms, persistence |
| actions | 行动数据、成本管线、可行性判定 | data/*.json |
| engine | 接收操作意图→校验→扣资源、记录行动 | actions, random |
| settlement | 掷骰后按 3.9–3.11 计算，产出明细与排名 | engine, goals |
| random | 服务端权威随机 | 无 |
| persistence | 快照、恢复、导出 | 无 |

## 5. 游戏流程（状态机）

```
LOBBY → GOAL_PICK → R1_PLAN(15:00) → R1_SETTLE → R2_PLAN(15:00) → R2_SETTLE → FINISHED
```

| 阶段 | 触发 | 行为 |
|------|------|------|
| LOBBY | 主持人建房 | 4 位房间码；玩家输码+昵称加入；分派 7 角色（+可选精算师） |
| GOAL_PICK | 主持人"开始游戏" | 每队发 2 张目标卡，城长选 1 保留 |
| R1_PLAN | GOAL_PICK 完成 | 抽第 1 轮事件卡全场公布；选行动（草稿可改、可放弃）；倒计时 15:00，剩 5:00/1:00 全场警示；城长标记特批 |
| R1_SETTLE | 主持人"开始结算" | 终审校验 → 掷骰动画 → 结算 → 明细逐步展示 → 排名（按当轮同公式小计排序，仅作过程参考） |
| R2_PLAN | 主持人"下一轮" | 资金重置（事件可改）、抽第 2 轮事件卡；行动池排除第 1 轮已选 |
| R2_SETTLE | 主持人"终局结算" | 同 R1_SETTLE + 目标卡判定 + 额外加分 + 终局排名 |
| FINISHED | 自动 | 颁奖台、成绩单、导出 JSON/CSV |

主持人可随时"强制开始"（缺位角色视为放弃）、提前结束规划、解锁已锁定行动、将违规行动强制改为放弃。

## 6. 通信协议（Socket.IO）

事件名与载荷集中在 `src/net/protocol.js`。

**客户端 → 服务端**

| 事件 | 载荷 | 说明 |
|------|------|------|
| room:create | {hostName} | 建房，返回房间码与主持人 token |
| room:join | {code, name} | 玩家加入，返回玩家 token |
| team:assign | {playerToken, teamId, roleId} | 分派队伍与角色（主持人和本人均可） |
| game:start | — | 主持人：进入 GOAL_PICK |
| goal:pick | {goalId} | 城长选保留卡 |
| action:select | {actionId} | 选/换行动草稿（校验失败返回原因） |
| action:lock | — | 锁定本角色行动 |
| action:pass | — | 声明放弃 |
| approval:grant | {type: REDUCE5 \| OVERDRAFT5, target?} | 城长特批 |
| phase:next | — | 主持人推进阶段 |
| force:unlock / force:pass | {roleId} | 主持人纠错 |
| game:resume | {roomCode, token} | 断线重连 |

**服务端 → 客户端**

| 事件 | 载荷 | 说明 |
|------|------|------|
| state:sync | 按身份过滤的快照 | 加入/重连/每次变更后 |
| timer:tick | {remaining, warning} | 服务端权威倒计时 |
| event:drawn | {cardId} | 事件卡公布 |
| dice:result | {teamId, kind, value, success} | 掷骰结果 |
| settle:step | {teamId, step, detail} | 结算明细逐项推送 |
| ranking:update | [{teamId, total, ...}] | 排行榜 |
| alert | {level, message} | 中文错误与警示 |

**信息可见性**：规划期行动草案队内可见、跨队只显示"已锁定/未锁定/放弃"；事件卡全场公开；目标卡候选与保留结果全场公开；骰子与结算全场公开。`state:sync` 按玩家身份过滤，服务端不向客户端发送其不可见状态。

## 7. 数据模型（服务端内存态，即快照格式）

```js
{
  code: "A1B2", hostToken, createdAt,
  phase: "LOBBY|GOAL_PICK|R1_PLAN|R1_SETTLE|R2_PLAN|R2_SETTLE|FINISHED",
  deadline: 1690000000000,          // 规划截止时间戳，null 表示无
  eventCards: { r1: "green_bond"|null, r2: "cold_wave"|null },
  players: [{ id, name, token, teamId|null, roleId|null, connected }],
  teams: [{
    id, name,
    goalCards: ["storage_master", "load_pioneer"], goalKept: "storage_master"|null,
    // 资源
    funds, landUsed, transCapExtra, storageCap,
    storageCarried,                 // 第1轮储能电量（仅第2轮可用）
    // 行动记录
    actions: { r1: { [roleId]: { actionId, locked, passed, approval,
                                  plannedConsume, actualConsume, powerOut, dice } | null },
               r2: { ... } },
    // 结算结果
    settlement: {
      r1: { power, available, planned, actual, stored, curtailed, penalized,
            penalty, shortage },
      r2: { ... },
      individual: { [roleId]: n },  // 含精算师
      extraBonus: [{ reason, points }],
      teamTotal, ranking
    },
    audit: [{ ts, who, what }]      // 违规提示、特批、强制操作留痕
  }]
}
```

规则常量（初始资源、行动、事件、目标卡）全部在 `data/*.json`，改版本只改配置。

## 8. 界面设计

视觉：能源绿主题；大屏深色背景、远距离可读；手机端大按钮、触控优先；纯 CSS 无框架。

### 8.1 加入页 `/`
房间码大号输入 + 昵称 + "我是主持人"入口。

### 8.2 玩家手机端 `/play`
- **大厅**：各队空缺角色一览，点选入队/选角色，"已就位"状态。
- **目标卡**：城长从 2 张公开候选中保留 1 张；其他玩家和大屏可查看候选与结果，但无选择按钮。
- **规划**（主界面）：顶部资源条（资金/土地/输配/储能 + 倒计时）→ 本角色行动卡列表（成本/产出/分数/**可行性实时标记**，不可行卡片置灰并标红原因，如"超输配上限：需 5，当前 3"）→ 选卡、锁定；城长多"特批"按钮；队友面板（队内草案互见）；事件卡横幅。
- **结算**：骰子动画 → 本队明细逐步点亮 → 实时排名。
- **终局**：本队成绩单、目标卡达成情况、颁奖。

### 8.3 主持人大屏 `/host`
- **大厅**：房间码 + 局域网二维码、队伍×角色分配矩阵。
- **规划**：全场进度矩阵（每队每角色 已锁定/未锁定/放弃）、倒计时、事件卡、阶段控制台——**不显示任何队草案**（大屏现场人人可见）。
- **结算**：全场骰子动画 → 逐队结算明细自动轮播 → 排行榜。
- **终局**：颁奖台（冠军队城长另标"卓越领袖奖"）、各队总分构成表、导出按钮。

## 9. 错误处理

| 场景 | 处理 |
|------|------|
| 非法操作（资源不足、重复行动等） | 服务端拒绝，回 `alert` 中文原因；客户端即时提示 |
| 玩家掉线 | token 断线重连，`state:sync` 全量恢复；规划结束仍未来者主持人可代"放弃" |
| 服务进程崩溃/重启 | 每次变更写 `data/snapshots/<code>.json`；重启后主持人凭房间码恢复 |
| 重复加入/角色冲突 | 校验拒绝并提示 |
| 本地改表加速倒计时 | 倒计时以服务端时间为准，客户端仅渲染 |
| 房间码冲突 | 随机重试直至唯一 |

## 11. 设计决策记录（规则模糊点的约定）

| # | 模糊点 | 约定 |
|---|--------|------|
| A1 | 计划消耗 > 可用绿电 | 实际消耗 = min(计划, 可用)；按申报顺序分配；缺口在明细中显著标注（正常游玩由精算师预警） |
| A2 | "÷4、÷5、÷10 取整" | 一律向下取整（分两处取整） |
| A3 | 寒潮对风电扣减 | 作用于掷骰后产出（15→12 或 5→2），下限 0 |
| A4 | 光伏/风电跨轮 | 行动产出仅当轮结算一次，故寒潮仅当发电企业当轮选了该源才扣减 |
| A5 | 违规 0 分条款 | 软件预先阻止违规（终审拦截），不采用"终局记 0"；留审计日志 |
| A6 | 全链降本是否含材料自身行动 | 含（材料行动也是全队行动之一，10−5=5） |
| A7 | 并列加赛 | 软件只显示并列与消纳模块净值，加赛线下由主持人按规则执行 |
| A8 | 特批与放弃 | 特批两项效果二选一、每轮 1 次，软件强制；放弃行动无产出无消耗 |
